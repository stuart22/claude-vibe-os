## Conventions

- Unit tests are the quality gate during implementation — run them as you build, not as a separate step
- Every feature implementation should end in a testable state the user can interact with
- Every user-facing feature needs an E2E test in `tests/e2e/` asserting on what the user sees
- Address Critical security findings before completing; defer Warnings with a note in `docs/decisions.md`

## Working with the User

The user is a product manager, not a software engineer:

- They don't read code — explain decisions in product terms
- Their feedback arrives as stream-of-consciousness testing notes (`vibe-os:feedback-triage` handles it)
- Summarize what changed from the user's perspective, not which files you edited
- Offer to let them test the running app at natural breakpoints

## Living Docs

You maintain these — check before decisions, update after changes:

- `docs/decisions.md` — check before architectural decisions, add entries after, flag contradictions
- `docs/architecture.md` — update on structural changes
- `docs/features/*.md` — update when implementation diverges from spec; don't silently deviate
- `docs/testing.md` — update the coverage map when E2E tests change

## Session Workflow

**Start:** read the relevant `docs/features/*.md` and `docs/decisions.md`.

**Build:** `superpowers:brainstorming` before creative work, `superpowers:writing-plans` for multi-step tasks, `superpowers:test-driven-development` while implementing, `superpowers:systematic-debugging` for bugs. `vibe-os:visual-check` after UI changes. `vibe-os:design-options` when a UI decision needs alternatives.

**Complete:** `superpowers:verification-before-completion`, then `vibe-os:quality-gate` (or `/check`), then `superpowers:finishing-a-development-branch`.

**Wrap up:** update the living docs above and commit them with the code.
